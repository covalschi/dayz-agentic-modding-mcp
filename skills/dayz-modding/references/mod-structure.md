# Mod structure & config.cpp reference

Complete config surface for DayZ mods. Verified against Bohemia wiki (Modding Structure /
Modding Basics), BI DayZ-Samples, CF, Dabs Framework and DayZ Expansion configs.

## Release folder layout

```
@MyMod/
├── addons/
│   ├── MyMod.pbo
│   └── MyMod.pbo.MyKey.bisign      # one .bisign per pbo per key
├── keys/
│   └── MyKey.bikey                 # public key — servers whitelist it
├── mod.cpp                         # in-game mod menu presentation
└── meta.cpp                        # workshop id/meta (generated by Publisher)
```

`mod.cpp` keys: `name`, `picture`, `logo`, `logoSmall`, `logoOver`, `tooltip`, `overview`,
`author`, `version`, `action` (URL button). Optional but looks professional.

Multi-PBO mods (Expansion-style): split content vs scripts per PBO; each PBO has its own
config.cpp; `requiredAddons` chains define load order.

## PBO prefix

Paths inside a PBO must equal the paths scripts/config reference
(`MyMod/scripts/4_World` in `files[]` ⇒ PBO contains `MyMod/scripts/4_World/...`).
Addon Builder derives the prefix from the source folder; a `$PBOPREFIX$` text file in the
source root overrides it (one line, e.g. `MyMod`). Prefix mismatch = mod loads but scripts
silently don't. Convention: prefix == mod dir name, lowercase inside samples ("mymod/...")
also works — stay consistent.

## CfgPatches (load order & dependency declaration)

```cpp
class CfgPatches
{
    class MyMod_Scripts
    {
        units[] = {};                 // legacy, usually empty
        weapons[] = {};
        requiredVersion = 0.1;
        requiredAddons[] =            // these load BEFORE this pbo
        {
            "DZ_Data",
            "DZ_Scripts",
            "JM_CF_Scripts"           // CF (if depending on CF)
            // "DF_Scripts"           // Dabs Framework
        };
    };
};
```

Overriding another mod's classes (e.g. patching a STALKER pack item): add THEIR CfgPatches
class name to your `requiredAddons` so your PBO loads after theirs, then `modded class`
their script class / override config values.

## CfgMods (script wiring & mod definition)

```cpp
class CfgMods
{
    class MyMod
    {
        dir = "MyMod";                       // mod root dir (matches prefix)
        name = "My Mod";
        credits = "YourName";
        author = "YourName";
        version = "1.0";                     // CF reads this (or versionPath)
        extra = 0;
        type = "mod";                        // MANDATORY
        storageVersion = 1;                  // enables CF_ModStorage (CF; >0)
        dependencies[] = {"Core", "GameLib", "Game", "World", "Mission"};   // the VMs this mod
                                             // touches: list "Core"/"GameLib" only when you declare
                                             // engine/gameLib modules below (CF, which has an
                                             // engineScriptModule, lists "Core"); usually
                                             // {"Game", "World", "Mission"}
        defines[] = {"MYMOD"};               // optional #ifdef symbols — here, beside dependencies[]

        // optional custom keybinds:
        inputs = "MyMod/data/inputs.xml";

        class defs
        {
            // GUI resources:
            class imageSets    { files[] = {"MyMod/gui/imagesets/mymod.imageset"}; };
            class widgetStyles { files[] = {"MyMod/gui/looknfeel/mymod.styles"}; };

            // script modules (any subset; folders, not files):
            class engineScriptModule  { value = ""; files[] = {"MyMod/scripts/1_Core"}; };
            class gameLibScriptModule { value = ""; files[] = {"MyMod/scripts/2_GameLib"}; };
            class gameScriptModule    { value = ""; files[] = {"MyMod/scripts/3_Game"}; };
            class worldScriptModule   { value = ""; files[] = {"MyMod/scripts/4_World"}; };
            class missionScriptModule { value = ""; files[] = {"MyMod/scripts/5_Mission"}; };
        };
    };
};
```

- `files[]` entries are **directories**; every `.c` under them (recursive) compiles into
  that VM. Order within a dir is alphabetical — if file A needs class from file B of the
  same tier, that's fine (two-pass compile), but cross-TIER visibility is strictly upward:
  4_World sees 3_Game, never vice versa.
- `value = ""` = no custom entry function (normal case).
- Missing `class imageSets` registration = images referenced from that set render silently
  BLANK (no error, no log) — register every `.imageset` file here.
- `defines[] = {"MYMOD", "MYMOD_FEATURE_X"};` inside the CfgMods class, beside
  `dependencies[]` (not inside `class defs`), declares
  extra preprocessor symbols usable with `#ifdef` in `.c` files — the compile-time gate for
  optional soft-dependencies (e.g. compile Expansion-integration code only when Expansion
  is loaded, without a hard requiredAddons entry). (community-reported, unverified): since
  DayZ 1.26 every CfgMods class NAME is also auto-registered as a define (e.g.
  `#ifdef DAYZEXPANSIONAI`).
- (community-reported, unverified): `type = "servermod"` instead of `"mod"` keeps the PBO's
  code off clients (pair with `-servermod=`). No occurrence found in a local modpack
  scan — verify before relying on it.
- Custom inputs: `inputs=` xml + read via `GetUApi().GetInputByName("MyInput")` — see
  BI sample Test_Inputs and the full reference in §Custom keybinds below.

## Custom keybinds (inputs.xml)

Full structure — new action + Controls-menu group + default key:

```xml
<modded_inputs>
  <inputs>
    <actions>
      <input name="UAMyModMenu" loc="STR_MYMOD_INPUT_OPEN" />
    </actions>
    <sorting name="mymod" loc="STR_MYMOD_INPUT_GROUP">
      <input name="UAMyModMenu" />
    </sorting>
  </inputs>
  <preset>
    <input name="UAMyModMenu">
      <btn name="kY" />
    </input>
  </preset>
</modded_inputs>
```

- `loc=` takes the BARE stringtable key — no `#`/`$` prefix (the system adds it).
- An input declared in `<actions>` but NOT listed in a `<sorting>` group is registered but
  INVISIBLE in the Controls settings. `visible="false"` on an input hides it from the
  rebinding UI on purpose.
- Modifier combos = nested `<btn>`, outer = modifier:
  `<btn name="kLControl"><btn name="mBLeft"/></btn>`. Multiple sibling `<btn>` = multiple
  default keys. Key-name convention: `kY`, `kLShift`, `mBLeft`.
- Input `name` must be globally unique across all loaded mods — prefix it.
- **Script polling**: cache once (`UAInput m_Input = GetUApi().GetInputByName("UAMyModMenu");`
  in init — never per frame), poll in modded `MissionGameplay.OnUpdate`. State methods
  (3_game\inputapi\uainput.c:58-65 in 1.30): `LocalValue()` (analog 0-1), `LocalPress()` (one frame
  on key-down), `LocalRelease()`, `LocalHold()` (every frame while held), `LocalHoldBegin()`,
  `LocalDoubleClick()`, `LocalClick()`. `ForceDisable(bool)` (uainput.c:94) while a menu is
  open. Per-input one-frame suppression is spelled `Supress()` — ONE 'p' (uainput.c:84);
  whole-API variant `GetUApi().SupressNextFrame(true)` (uainput.c:265) is what vanilla
  calls when closing menus to avoid input bleed (missiongameplay.c:1026);
  `GetUApi().UpdateControls()` after each exclusion change (uainput.c:237).
- **Silent-fail checklist** — a broken keybind produces ZERO log output; all three pieces
  must align: (1) correct inputs.xml structure (above; a binding-only short form
  `<modded_inputs><action name="..." preset="default"><key name="KC_F4"/></action></modded_inputs>`
  is community-documented for rebinding EXISTING actions), (2) CfgMods registration
  `inputs = "MyMod/inputs.xml";`, (3) the RIGHT poll method — `LocalPress` fires once on
  key-down, `LocalHold` every frame, `LocalRelease` on key-up; polling the wrong one looks
  identical to "not registered".

### Voice (VoN): a mod cannot make the player talk

Measured against 1.29 (124708) sources, 2026-09-02; line numbers below are 1.30.164200.
What script gets about voice (also on `Game`, unlisted here: `SetVoiceEffect`, `MutePlayer`,
`MuteAllPlayers`, and `EnableMicCapture`, which "does NOT automatically get transmitted over
network"):

| symbol | where | what it actually does |
|---|---|---|
| `proto native void EnableVoN(Object player, bool enable)` | `Game` (game.c:1055) | PERMISSION, not transmission. Vanilla calls it with `false` to silence a killed or unconscious player (playerbase.c:1233, 3799) and with `true` when an unconscious player comes round (playerbase.c:3856) |
| `SetVoiceLevel(int)` / `GetVoiceLevel(Object)` | `Game` (game.c:1069, 1074) | whisper/talk/shout distance (`enum VoiceLevel`, constants.c:17) |
| `VONManager.HandleInput` | 3_game/vonmanager.c:116 | reads ONLY `UAVoiceDistanceUp/Down`; never transmission |

**Transmitting is the native input `UAVoiceOverNet` (hold) / `UAVoiceOverNetToggle`
(doubleclick), and there is no script call for it.** A mod that wants "press my key and
also talk" cannot do it in code.

What a mod CAN do is read the state, live and client-side:

- `VONStateEventTypeID` fires with `VONStateEventParams` = `Param2<bool,bool>` —
  param1 "VoN active", param2 "toggled mode" (gameplay.c:447-553);
- `VONManager` writes param1 into `Mission.SetVoNActive()`, so
  `GetGame().GetMission().IsVoNActive()` is a live boolean (missiongameplay.c:1648);
- `VONManagerBase.m_OnVonStateEvent` is a public `ScriptInvoker` fired on every change
  (vonmanager.c:4, 261) — subscribe instead of polling.

**The practical answer to "one key for both" is BINDINGS, not code.** An input element in
the preset XML takes several `<btn>` children, so `UAVoiceOverNet` can carry a second key
alongside its default, and a mod's own PTT input can share that key. Both inputs then fire
from one press. Verified on a live client 2026-09-02: `UAVoiceOverNet` on kCapital plus
kEnd, a mod PTT on kEnd alone — CapsLock spoke locally only, End spoke locally and opened
the mod's transmitter.

## Script tier cheat-sheet

| Tier | Sees | Typical mod content |
|---|---|---|
| 1_Core | engine | rarely touched; low-level defines |
| 2_GameLib | +1_Core | rarely touched |
| 3_Game | +2_GameLib | settings classes, RPC managers, constants, JSON data classes, `DayZGame` mods |
| 4_World | +3_Game | items, devices, actions, recipes, PlayerBase mods, world managers |
| 5_Mission | +4_World | MissionServer/MissionGameplay mods, UI menus, HUD |

Client vs server: all tiers load on both; `MissionServer` exists only server-side,
`MissionGameplay` only client-side — they are the natural per-side entry points.

## Localization (stringtable)

Per-mod `stringtable.csv` at the mod root (see BI sample Test_Stringtable). The file starts
with a UTF-8 BOM and uses CRLF; the header is vanilla's, copied from `dta/languagecore`:

```csv
"Language","original","english","czech","german","russian","polish","hungarian","italian","spanish","french","chinese","japanese","portuguese","chinesesimp",
"STR_mymod_analyze","Analyze sample","Analyze sample","Analyze sample","Analyze sample","Analyze sample","Analyze sample","Analyze sample","Analyze sample","Analyze sample","Analyze sample","Analyze sample","Analyze sample","Analyze sample","Analyze sample",
```

Reference it as `$STR_mymod_analyze` in config.cpp (`displayName`, `descriptionShort` —
vanilla: `displayName = "$STR_CfgVehicles_SodaCan_Pipsi0";`, DZ\gear\drinks\config.cpp:621)
and as `#STR_mymod_analyze` in scripts (`m_Text`, `SetText`) and .layout files; inputs.xml
`loc=` takes the bare key.
Column set MUST match the vanilla list -- measured 2026-09-04: a table with only
`original,english` makes the client show the raw key for every string (the
header, every button). Vanilla form (`dta/languagecore`): UTF-8 BOM, every cell
quoted, a trailing comma after the last cell, CRLF; fourteen languages:
original, english, czech, german, russian, polish, hungarian, italian, spanish,
french, chinese, japanese, portuguese, chinesesimp. The client's language is
`language="English";` in `<-profiles>/Users/<name>/DayZ.cfg`, read at start; a
client set to Russian showed the `russian` column's text (measured). What an
EMPTY cell falls back to (english or original) is not measured -- so fill every
non-English column (with the original-language text) instead of leaving cells empty.
Note: `"original"` column is the source language, used when the game language has no column.

Reading strings from SCRIPT (measured 2026-09-20 on the dedicated server): the engine
resolves `$STR_` keys on the server too -- `GetGame().ConfigGetText("CfgVehicles Apple
displayName", s)` gives `Apple`, `AKM` gives `KA-M` -- in the SERVER's language (its
`language=`; unset = English). A key no table holds comes back as the key without `$`
(`STR_DN_UNKNOWN`); a string the engine holds only in the original column comes back with
a `$UNT$` prefix (`$UNT$Mouflon Steak`). `ConfigGetTextRaw` gives the raw `$STR_...`,
`ConfigGetBaseName` the parent class, `ConfigGetChildrenCount/ConfigGetChildName` walk a
root (12 937 classes of five roots in ~1 s). Only ONE language is live at a time -- no
script API translates into another (`Widget.TranslateString` uses the same table) -- so
for a second column read the `stringtable.csv` files yourself with `OpenFile` (readable
inside PBOs, see persistence-networking.md "File I/O"): a script reader of the
`original`+`english` columns read 6 tables / 7301 keys in under a second.
Vanilla's ITEM names are NOT in `dta/languagecore` (7247 lines of UI/tutorial text); the
engine resolves them from tables the script cannot open.

## Overriding vanilla configs

Redeclare the class with the changed properties (config merge is per-property):

```cpp
class CfgVehicles
{
    class PersonalRadio;                       // declare external
    class PersonalRadio_Custom : PersonalRadio // new variant
    { displayName = "Lab Terminal"; };

    // or change the vanilla item itself (+ requiredAddons "DZ_Gear_Drinks": the class lives in
    // DZ\gear\drinks\config.cpp:618 as `class SodaCan_Pipsi: SodaCan_ColorBase`):
    class SodaCan_ColorBase;                   // declare the vanilla parent
    class SodaCan_Pipsi : SodaCan_ColorBase    // keep the parent, or the class is re-based
    { descriptionShort = "..."; };
};
```

Script-side equivalents use `modded class`. Config override wins by load order
(requiredAddons). Check real vanilla config values by extracting game PBOs (Addons/*.pbo →
config.bin — binarized; use `CfgConvert` from DayZ Tools to convert bin→cpp, or read the
wiki/community dumps).

## Multi-mod compatibility rules

- Never edit vanilla files; only `modded class` + config subclassing.
- Always `super.…()` in modded overrides.
- Unique global names: prefix EVERYTHING (`MyMod_`) — classes,
  stringtable keys, RPC names, profile folders.
- Feature-detect other mods at runtime: `GetGame().ConfigIsExisting("CfgMods StalkerPackX")`
  or CF `ModLoader.Contains("...")` (bool; `ModLoader.Find(name, out ModStructure mod)` when
  you need the entry) — degrade gracefully when absent.
